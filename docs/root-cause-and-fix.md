# The root cause, and how it was fixed

This is the document that explains why the original attempt failed and what
replaced it. Read this before touching the print path.

## The symptom

The hand-written Rust QPDL encoder produced streams that the HP Laser 107a
accepted without complaint:

- no `SPL ERROR`,
- the firmware consumed every byte,
- and then it silently completed **without feeding paper**.

Roughly ten supervised test pages were spent bisecting QPDL version,
page-header dimensions, paper-type bytes, band sequencing and PJL header
content. The missing invariant was never found, and the work was parked.

## The cause

The Samsung engine in this printer (M2020/M2026 family) **rejects — silently —
any page whose band width is not exactly one of a fixed set of values**. It is
not a formula and not an alignment rule: it is a lookup table taken from
Samsung's own ULD driver, keyed on paper type and resolution.

The natural assumption, and the one the original encoder made, is:

```c
bandWidthInB = (pageWidth + 7) / 8;   // wrong for this engine
```

For US Letter at 600 dpi that yields **638** bytes. The printer wants **640**.
Two bytes per band is enough to make it discard the page without a word.

splix carries the real table. In `src/compress.cpp`:

```c
/* Look up bandwidths in bytes generated by Samsung ULD for 2020 series
 * Samsung M2026 does not work unless it receives _exactly_ the right bandwidths
 * There does not seem to be a general formula for all paper sizes, hence simple lookup */
unsigned long _get2020BandWidthInB(unsigned char papertype,
                                   unsigned long xresolution,
                                   unsigned long inputwidth)
```

A 26-entry table, for example:

| paper | 600 dpi | 1200 dpi |
|---|---|---|
| Letter | 640 | 1248 |
| A4 | 608 | 1216 |
| A5 | 416 | 832 |
| Legal | 640 | 1248 |
| Executive | 544 | 1056 |

The lookup is gated on a PPD attribute, and that attribute is the whole
switch:

```
*QPDL SpecialBandWidth: True
```

`src/compress.cpp` branches three ways — `specialBandWidth()` (this table),
`fixedBandWidth()` (one constant, legacy QPDL v1/v2 models), or the naive
line width. The HP Laser 10x PPD sets **only** `SpecialBandWidth`.

Support for this printer landed in **splix 2.0.2** (commit `206e283`,
"Add support for Samsung M2020 series, HP Laser 10x, Laser MFP 13x").
Debian and Ubuntu still ship 2.0.1, which does **not** have it, so
`apt-get install printer-driver-splix` is not a fix. Neither is
`ml2010.ppd` or `ml1660.ppd` — the correct PPD is **`laser10x.ppd`**.

## The proof

`app/verify-bandwidth.sh` runs the same CUPS raster through the shipped filter
twice — once with the gate, once with that single PPD line deleted — and
decodes the band width straight out of the emitted QPDL band headers
(`header[2..3]`, big-endian, written at `src/qpdl.cpp:186`):

```
with gate (shipped)    4 bands, width 5120 bits = 640 bytes
without gate           4 bands, width 5104 bits = 638 bytes
```

640 bytes is Letter @ 600 dpi from the table. 638 is the naive line width.
This reproduces the original silent failure on demand, offline, with no
printer and no paper.

## The architecture now

```
  iPhone / iPad / MacBook
        │  AirPrint (IPP Everywhere)
        ▼
  macOS Printer Sharing  ── cupsd, Bonjour, image/urf + PWG raster
        │
        ▼
  CUPS queue "HPLaser107a"
        │  PPD: laser10x.ppd  (SpecialBandWidth: True)
        ▼
  rastertoqpdl            ── splix 2.0.2, built for arm64
        │  QPDL / SPL2, 640-byte bands
        ▼
  /usr/libexec/cups/backend/usb
        │
        ▼
  HP Laser 107a (USB 03F0:E82A)
```

The hand-written IPP server and AirPrint advertisement are no longer needed:
macOS's own Printer Sharing already advertises the queue over Bonjour and
renders jobs locally through the queue's driver, so clients need no driver for
the printer. That is the supported way to expose a USB-only printer to iOS.

## Why the Rust encoder is archived

`src/` is kept for reference only. It is not on the print path. Its USB
transport, PWG-Raster decoder and multi-model registry all work; the QPDL band
encoder is the part that was wrong, and there is no reason to finish it now
that a maintained driver with the correct table exists and has been proven
against the same reference raster.

## Verified, and not yet verified

Verified offline, no hardware needed:

- splix 2.0.2 builds natively for arm64 with Command Line Tools only.
- The shipped filter and PPD emit 640-byte bands for Letter @ 600 dpi.
- Removing the gate reproduces the original failure (638-byte bands).
- The app builds, launches, and reads real queue state from CUPS.

**Not yet verified — needs the printer plugged in:**

- That the printer accepts the stream and physically feeds paper.
- That the queue survives a real job end to end.

Everything up to USB transmission is proven; the last hop is untested.
